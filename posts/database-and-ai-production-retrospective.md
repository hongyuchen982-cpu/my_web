这个网站在本地开发时运行得很顺利：SQLite 保存文章和项目，Ollama 提供聊天与向量模型，Next.js 页面可以直接读取数据，RAG 也能完成检索和回答。

真正准备上线时，我才发现“本地能跑”与“公网可用”之间还有一整条链路。数据库换了运行环境，模型换了提供商，环境变量也从本地文件转移到部署平台。任何一处没有同步，最终表现都可能只是页面空白、AI 没有回答，或者检索永远找不到内容。

这篇文章记录我在数据库和 AI 上线过程中遇到的主要问题，以及最后采用的解决方式。

## 一、本地环境和线上环境并不是同一套系统

本地开发使用的是：

```text
Next.js
  ├─ SQLite：文章、项目、知识切片和向量
  └─ Ollama
      ├─ qwen2.5:3b：生成回答
      └─ qwen3-embedding:0.6b：生成向量
```

线上部署则变成：

```text
Vercel / 生产服务器
  ├─ Turso：远程 libSQL 数据库
  ├─ OpenRouter 等云端聊天接口
  └─ OpenAI-compatible Embedding 接口
```

代码虽然是同一份，但数据、模型和密钥都不是同一份。最初我把注意力放在“构建是否成功”，后来才意识到：生产构建通过，只能证明代码可以编译，不能证明云数据库里有数据，也不能证明模型账号、配额和向量索引已经可用。

## 二、数据库接上了，页面为什么还是空的

### 1. 本地 SQLite 数据不会自动进入 Turso

本地文章保存在 `dev.db`。部署到线上后，应用通过 `TURSO_DATABASE_URL` 和 `TURSO_AUTH_TOKEN` 连接远程数据库。

这时即使数据库连接成功，Turso 也可能还是空库。Prisma Schema 只描述表结构，不会自动把本地文章和项目复制过去。

我最后把数据库上线拆成三个步骤：

1. 在云数据库执行迁移，建立当前代码需要的表；
2. 把已发布文章和项目同步到 Turso；
3. 查询线上记录数量，并直接访问页面确认数据真的存在。

只做第一步，页面不会报数据库连接错误，却可能因为 `Post` 和 `Project` 表没有内容而显示空列表。

### 2. 开发环境必须固定使用本地数据库

另一个容易忽略的问题是连接优先级。如果本地开发时误读了 Turso 环境变量，调试过程可能直接修改线上数据。

我在数据库初始化中明确区分环境：

```ts
const url = process.env.NODE_ENV === "production"
  ? remoteUrl || localUrl
  : localUrl || remoteUrl || "file:./dev.db";
```

开发环境优先使用 `DATABASE_URL=file:./dev.db`，生产环境才优先使用 Turso。这样本地调试不会因为环境文件中同时存在云端配置而意外绕到远程数据库。

### 3. 改 Markdown 不等于改了线上文章

这个网站运行时从数据库读取文章，`posts/` 目录中的 Markdown 是版本化内容源。修改 Markdown 后还要执行内容同步：

```bash
npm run content:sync
npm run content:sync -- --cloud
```

第一条更新本地数据库，第二条更新 Turso。这个区别很重要：文件正确、本地数据库正确、线上数据库正确，是三个需要分别确认的状态。

### 4. 数据迁移不能只看“命令没有报错”

我会在同步后继续核对：

- 已发布文章数量；
- 项目数量；
- 每篇文章的作者关联；
- 新增表是否真正存在；
- 应当删除的旧文章是否还在。

只有这些结果和预期一致，数据库迁移才算完成。

## 三、Ollama 能用，为什么线上 AI 不能直接照搬

Ollama 运行在本机的 `127.0.0.1:11434`。部署到 Vercel 后，服务器中的 `127.0.0.1` 指向云端实例本身，不会连接到我的电脑。

因此，公网 AI 必须使用云端可访问的 HTTPS 接口，或者把 Ollama 部署到一台长期运行、受保护的服务器上。不能把本地地址直接复制进生产环境变量。

我最后保留两套模式：

- 本地使用 Ollama，方便免费调试；
- 线上使用 OpenRouter、硅基流动或其他兼容接口。

模型配置只在服务端读取，API Key 不进入浏览器，也不使用 `NEXT_PUBLIC_` 前缀。

## 四、聊天模型和 Embedding 不是同一个配置

这是 AI 上线时最容易混淆的一点。

聊天模型负责根据检索结果组织回答；Embedding 模型负责把文章、代码和问题转成向量。即使某个平台提供免费聊天模型，也不代表它同时提供免费向量接口。

线上需要分别配置：

```text
CHAT_PROVIDER
CHAT_MODEL
CHAT_API_KEY / OPENROUTER_API_KEY

EMBEDDING_PROVIDER
EMBEDDING_BASE_URL
EMBEDDING_MODEL
EMBEDDING_API_KEY
```

如果只配置聊天模型，AI 可能能够生成文本，但 RAG 没有问题向量，无法从知识库检索相关内容。如果只配置 Embedding，检索能够找到切片，却没有模型负责生成最终回答。

我把两套配置彻底拆开，避免再用一个 `AI_PROVIDER` 同时猜测聊天和向量服务。

## 五、更换 Embedding 后，旧向量为什么不能继续用

不同 Embedding 模型的向量维度和语义空间可能不同。文档使用模型 A 生成向量，问题却使用模型 B 生成向量，两者即使维度碰巧相同，相似度也没有可靠意义。

因此更换线上 Embedding 模型后，我会：

1. 暂停或限制公开问答；
2. 使用新模型重新生成全部文章和项目向量；
3. 确认数据库记录的 `embeddingModel` 与当前配置一致；
4. 重新运行已知问题和未知问题评测；
5. 根据新模型结果重新校准检索阈值。

“数据库里已经有向量”并不够，必须确认它们来自当前正在使用的模型。

## 六、云端免费模型还带来了哪些问题

### 1. 免费模型列表会变化

免费模型可能下线、限流或临时不可用，因此不能把一次查询到的列表永久写死。我让服务端读取当前目录，只保留价格为零的文本模型，并提供免费路由作为可控回退。

### 2. 认证失败不能盲目重试

遇到限流或临时服务错误，可以尝试另一个免费路由；但 API Key 无效属于配置问题。认证失败如果持续重试，不会自行恢复，只会制造更多无效请求。

### 3. 前端不能任意指定模型和接口

模型选择必须经过服务端白名单验证。浏览器不能提交任意上游地址或自己的密钥，否则会产生 SSRF、费用失控和密钥泄露风险。

### 4. 一个问题可能触发多次调用

完整 RAG 流程不一定只调用一次模型。它可能包含问题向量、答案生成、引用检查和失败后的重写。所谓“免费额度”是整个账号共享的，不能按一次点击等于一次调用来估算。

## 七、Vercel 上不适合长期运行知识库 Worker

项目同步、文档切片和批量向量化可能持续较长时间。Vercel Serverless 请求有执行时长和生命周期限制，不适合作为长期后台 Worker。

我的处理方式是把任务状态写入数据库，再由独立 Worker 消费：

```text
管理后台提交任务
      ↓
KnowledgeJob = queued
      ↓
独立 Worker 执行同步 / 切片 / 向量化
      ↓
数据库记录完成状态或错误
```

这样 Web 请求可以快速返回，耗时任务也不会因为页面请求结束而被中断。Worker 还需要避免重复启动，否则同一个知识库任务可能被并发执行并重复产生模型费用。

## 八、最后建立一套上线检查

为了避免每次部署都靠人工回忆，我增加了上线检查脚本。它不会打印密钥，只验证关键条件：

- 管理密码和会话密钥长度是否足够；
- 生产数据库是否可以访问；
- 聊天提供商和模型是否配置；
- Embedding 是否使用 HTTPS 接口；
- 当前 Embedding 模型是否已经生成向量；
- 文章和项目数量是否正常。

静态检查通过后，我还会实际完成一次网页问答、一次未知问题拒答、一次 HTTPS 登录和一次数据库备份恢复演练。只有真实链路通过，AI 才算真正上线。

## 总结

这次上线最重要的经验，是不要把“本地功能正常”当作“生产系统已经就绪”。

数据库需要分别处理表结构、内容和作者关联；AI 需要分别处理聊天模型、Embedding、向量重建和后台任务；部署平台还要正确保存所有服务端环境变量。

我最后把整条链路归纳为：

```text
迁移表结构
  ↓
同步文章与项目
  ↓
配置云端聊天模型
  ↓
配置 Embedding
  ↓
重建向量
  ↓
启动 Worker
  ↓
运行上线检查和真实问答
```

任何一步缺失，网站都可能“看起来已经部署”，但数据库或 AI 实际上仍不可用。把这些步骤拆开验证后，问题才真正变得可定位、可恢复，也能在下一次部署时重复执行。
