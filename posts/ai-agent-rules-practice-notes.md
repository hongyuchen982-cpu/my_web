在项目里使用 Coding Agent 久了，我发现很多“AI 不听话”的问题，其实不完全是模型能力问题，而是上下文问题。

新开一个会话后，Agent 并不知道这个项目解决什么业务、真正使用什么技术栈、哪些目录不能碰，也不知道我希望它改完后执行哪些验证。信息不够时，它只能重新搜索代码，甚至根据常见项目结构去猜。于是就会出现重复造轮子、改动范围过大、使用过时 API、遗漏测试等问题。

我现在会在项目根目录维护一份规则文件，把那些“Agent 不知道就容易做错”的事实固定下来。对我来说，它不是一段万能提示词，而是项目文档和开发流程的一部分。

## 一、规则文件解决什么问题

聊天里的临时要求只对当前上下文有效。规则文件则会随项目保存，让 Agent 每次开始工作时都能先读取相同的基础信息。

一份有效的规则文件主要解决四类问题：

- **项目认知**：这个项目是做什么的，当前处于什么阶段；
- **定位效率**：核心目录、数据入口和关键文件在哪里；
- **修改边界**：哪些能力应该复用，哪些文件不能修改；
- **交付标准**：完成后要运行什么测试，怎样说明结果。

规则写清楚后，我不需要在每次对话里重复解释项目背景，也能减少 Agent 因为信息不足而做出的错误假设。

## 二、文件放在哪里

不同 Coding Agent 使用的项目说明入口不完全相同。我常用的两类文件是：

| 工具 | 项目规则文件 |
|---|---|
| Codex 及支持同类约定的工具 | `AGENTS.md` |
| Claude Code | `CLAUDE.md` |

文件通常放在项目根目录。一个仓库如果需要兼容多个工具，我会选择一份作为主要规则，另一份只保留简短入口，避免维护两套逐渐不一致的内容。

以这个个人网站为例，根目录里的 `AGENTS.md` 会提醒 Agent：当前 Next.js 版本有破坏性变化，写代码前必须先阅读项目安装包中的对应文档。这条规则很短，却会直接改变 Agent 的工作方式。

## 三、先让 Agent 读懂项目，再生成初稿

规则文件可以手写，也可以让 Agent 先扫描项目后生成初稿。我更常用第二种方式，因为它能从现有代码、依赖和脚本中提取真实信息。

我会这样描述任务：

```text
请先阅读这个项目的 package.json、目录结构、数据库配置和现有文档，
再在项目根目录生成一份 AGENTS.md。

内容至少包括：
1. 项目目标与业务边界；
2. 技术栈和准确版本；
3. 核心目录、数据入口与关键文件；
4. 安装、开发、测试和生产构建命令；
5. 代码规范与禁止修改的目录；
6. 修改后的验证要求；
7. 遇到关键歧义时如何处理。

不要根据常见项目猜测，只写能够从当前仓库确认的事实。
```

有些工具提供初始化命令，也可以用来生成第一版。但无论通过什么方式生成，我都会亲自检查一遍。自动生成的内容容易漏掉本地与生产环境差异，也可能把已经失效的命令写进去。

## 四、我会写进规则文件的七类内容

### 1. 项目目标

先用一两段话说明业务场景、目标用户和明确边界。规则首先要回答“这是什么项目”，而不是一上来就堆代码风格。

### 2. 技术栈与运行环境

语言、框架、运行时、包管理器、数据库和关键依赖都要写准确版本。版本很重要，同一个框架在不同大版本中可能已经改变 API、文件结构和默认行为。

### 3. 架构与关键文件

只列真正影响定位的内容，不必把整个目录树复制进去。例如这个网站的公开文章链路可以写成：

```text
文章页面
  ↓
src/lib/posts.ts
  ↓
Prisma
  ↓
本地 SQLite / 线上 Turso
```

Agent 看到这条数据流后，就知道只改页面组件并不能改变数据库中的文章正文。

### 4. 常用命令

至少写明安装依赖、启动开发环境、运行测试、代码检查和生产构建命令。如果还有数据库迁移、内容同步、索引重建等脚本，也要说明用途，以及它会不会修改外部数据。

### 5. 测试与验证

“代码写完”不等于任务完成。我会明确要求 Agent 根据改动运行对应测试，并在交付时说明哪些检查通过、哪些因为环境限制没有执行。

### 6. 修改边界

这里记录容易造成返工的约束，例如：

- 优先复用已有组件和工具函数；
- 不为了一个小功能引入大型依赖；
- 不修改生成目录；
- 保留用户已有的未提交改动；
- 涉及删除、覆盖或外部发布时先确认目标。

### 7. 工作原则

我更关心 Agent 怎样做决定，而不只是代码缩进。有效的原则通常包括：先阅读相关代码、公开必要假设、优先最小改动、遇到会改变结果的歧义时停止猜测，以及完成后给出可核对的验证结果。

## 五、规则不是越多越好

规则文件一旦写得太长，真正重要的约束反而会被淹没。我判断一条内容是否值得放进去时，会问三个问题：

1. Agent 不知道它时，是否很容易做错？
2. 它是否会在多个任务里反复出现？
3. 它现在是否仍符合代码和部署环境？

如果答案大多是否，这条内容更适合留在 README、设计文档、Issue 或当前任务说明中。

我也不会把某次偶发报错的全部排查过程塞进规则文件。规则记录的是稳定决策依据，不是项目的所有历史。

## 六、规则文件需要持续维护

项目会变化，规则也会过期。依赖升级、目录调整、部署平台更换、数据库迁移或新增测试脚本后，我都会顺手检查相关规则。

维护时我会让 Agent 先对照代码验证旧规则，再做小范围更新。例如：

```text
请核对 AGENTS.md 中的技术栈、命令和目录说明是否仍与当前仓库一致。
只修改已经过期或缺失的部分，并说明每一处修改依据。
```

这样可以避免规则文件逐渐变成一份“看起来很完整、实际上不能用”的旧文档。

## 七、我现在使用的通用模板

下面这份模板适合作为起点。它不是必须原样照搬的标准，我会根据项目规模删减。

````md
# 项目说明

## 项目概述
- 这个项目解决什么问题：
- 当前主要功能：
- 明确不在范围内的内容：

## 技术栈与环境
- 语言与版本：
- 框架与版本：
- 包管理器：
- 数据库与外部服务：
- 本地和生产环境的差异：

## 架构与关键文件
- 数据入口：
- 页面或接口：
- 核心业务逻辑：
- 数据访问层：
- 配置文件：
- 禁止手动修改的生成目录：

## 常用命令
```bash
# 安装依赖

# 启动开发环境

# 运行测试

# 代码检查

# 生产构建
```

## 代码规范与修改边界
- 修改前先阅读相关实现。
- 优先复用现有组件和工具函数。
- 不做与当前任务无关的重构。
- 不覆盖用户已有的未提交改动。
- 不在没有说明的情况下新增大型依赖。

## 验证要求
- 运行与改动直接相关的测试。
- 高风险改动补充生产构建或接口验证。
- 无法执行的检查必须如实说明。

## 工作原则
- 先理解，再修改。
- 使用能够从仓库确认的事实，不凭经验猜版本和结构。
- 在不改变需求的前提下做合理假设并继续推进。
- 歧义会显著改变结果时，向用户确认。
- 完成后说明改了什么、验证了什么、还剩什么风险。
````

## 结语

规则文件不能让 Agent 永远不犯错，但它能显著减少因为上下文缺失造成的误判。

我把它当成一份写给“第一次进入这个仓库的人”的操作说明：内容不需要多，重点是准确、稳定、能影响实际决策。只要项目变化时同步维护，它就会成为 Coding Agent 最有价值的上下文入口之一。
