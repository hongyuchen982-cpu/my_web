在个人项目里使用 Coding Agent 时，我反复遇到过几类问题：它不了解项目边界、重复引入已有能力、修改了无关文件，或者在缺少信息时直接猜测。

这些现象不一定说明模型能力不足。很多时候，真正缺少的是一份稳定、明确、可以随项目一起维护的上下文。规则文件的意义，就是把那些“Agent 不知道就很容易做错”的信息固定下来。

## 一、规则文件解决什么问题

新会话通常不会自动继承此前所有讨论。仅靠聊天里临时强调约束，时间一长很容易失效。

项目规则文件可以在每次工作前提供一份最小但稳定的说明，包括：

- 项目解决什么问题；
- 当前实际使用的技术栈与版本；
- 核心目录、数据入口和关键文件；
- 安装、开发、测试和构建命令；
- 代码风格、修改边界和验证要求；
- 遇到不确定情况时应当如何处理。

对我来说，规则文件不是“万能提示词”，而是项目自身的一部分。代码变化后，规则也需要跟着更新。

## 二、不同工具中的文件位置

| 工具 | 常见的项目规则文件 |
|---|---|
| Codex 及兼容工具 | `AGENTS.md` |
| Claude Code | `CLAUDE.md` |

如果同一个项目需要兼容多个 Agent，我更倾向于维护一份主要规则，再让其他入口引用它，避免两套规则长期漂移。具体引用方式应以工具当前版本的官方文档为准。

## 三、我会写进规则文件的内容

### 1. 项目目标

用一两段话解释业务场景、目标用户和明确边界。规则首先要让 Agent 知道“这个项目是什么”，而不是直接堆编码要求。

### 2. 技术栈与运行环境

准确写出语言、框架、运行时、包管理器、数据库和关键依赖版本。版本信息非常重要，因为新版本可能已经改变 API、目录结构或约定。

### 3. 架构与关键文件

列出真正重要的目录和数据流，让 Agent 能快速判断应该读取和修改哪里。例如：

```text
页面 / Route Handler
        ↓
业务与安全校验
        ↓
Prisma 数据访问
        ↓
SQLite / Turso
```

### 4. 常用命令

至少写明：

```bash
npm install
npm run dev
npm test
npm run lint
npm run build
```

如果项目还有迁移、索引、数据同步等特殊脚本，也应该说明其用途和风险。

### 5. 测试与验证

仅仅要求“改完代码”是不够的。规则需要告诉 Agent 如何证明改动有效，例如运行单元测试、生产构建、接口冒烟测试，以及检查移动端和桌面端页面。

### 6. 修改边界

我会明确要求优先复用已有组件、不要随意加入大型依赖、不修改生成目录，并保护用户已有的未提交改动。

### 7. 工作原则

比代码风格更重要的是决策方式：先理解再修改、优先最小改动、公开假设、遇到关键歧义时停止猜测，以及在完成后清楚说明验证结果。

## 四、规则不应该无限增长

规则越长，不一定越有效。大量低频信息会占用上下文，也会掩盖真正重要的约束。

我判断一条内容是否应该进入规则文件时，会问三个问题：

1. Agent 不知道它时，是否很容易犯错？
2. 它是否会在多个任务中重复出现？
3. 它是否仍然符合当前代码和部署环境？

如果三个问题都是否，这条内容更适合留在普通文档、Issue 或当前任务说明里。

## 五、从这次网站维护中得到的体会

这个个人网站在本地使用 SQLite 和 Ollama，公网则使用 Turso、OpenRouter 与 Vercel。聊天模型和 Embedding 模型必须分别配置；云数据库新增表后还需要实际执行迁移。

如果规则文件只写“这是 Next.js 项目”，Agent 就很容易忽略这些真实差异。有效的规则必须记录会改变决策的事实，例如：

- 写代码前读取当前 Next.js 版本自带文档；
- 本地数据库与公网数据库不是同一个运行环境；
- 密钥只能进入环境变量，不能提交 GitHub；
- Fork 和外部开源项目只能作为参考，不能放进个人原创项目列表；
- 文章迁移只保留作者自己的正文，旧博客主题和相关推荐不属于文章内容。

规则文件真正的价值，不是让 Agent 永远服从一套死规则，而是降低上下文缺失带来的误判。

## 六、一次真实问题复盘：让个人博客重新只代表我自己

这次维护网站时，我遇到的并不只是一个页面显示问题，而是更重要的**内容归属问题**。

### 出现了什么问题

网站的项目列表混入了我 Fork 的开源仓库，项目详情页又会直接读取并展示仓库 README。这样一来，第三方项目原作者写下的介绍、团队信息和技术说明，就可能出现在我的个人作品页里，看起来像是由我原创或独立完成。

文章迁移也有类似风险。旧博客页面除了我的整理和实践记录，还可能包含外部文章的介绍、主题模板内容、相关推荐和原作者信息。如果把整个页面直接搬进新网站，就无法清楚区分哪些是我的经验，哪些只是引用材料。

与此同时，本地 SQLite、云端 Turso 和 GitHub 仓库是三套不同的数据状态。只修改本地页面，并不代表公网数据库已经同步；只修改云端数据，也不能保证下一次部署后仍然保持一致。

### 我如何解决

我先确认了 GitHub 仓库的真实属性，把项目分成两类：

- 我创建或实际参与维护的项目，进入个人项目列表；
- Fork 与第三方开源仓库，只能进入明确标注原作者的学习参考区域。

随后，我重新编写了每个个人项目的介绍，只描述我实际完成、参与或正在实践的内容。项目详情页不再把完整 README 当成“我的项目介绍”，而是把 README 放到独立的“仓库文档”入口中。这样即使文档包含协作者或外部资料，也不会和我的个人陈述混在一起。

对于文章，我没有直接复制旧网页，而是提取真实的排查过程和个人思考，重新组织成第一人称文章。外部论文、旧页面和他人材料只保留在“参考说明”中，并明确写出它们不属于我的原创内容。

为了避免以后再次出现本地与公网内容不一致，我还增加了版本化的内容同步脚本。文章正文和个人项目说明保存在代码仓库中，同一个脚本可以分别同步本地数据库与 Turso 云数据库。同步时还会移除已知的 Fork 展示记录，但不会删除 GitHub 上的仓库本身。

最后，我依次完成了以下验证：

1. 检查云端数据库中保留的项目数量和文章记录；
2. 运行自动化测试与代码检查；
3. 执行 Next.js 生产构建；
4. 推送 GitHub，并等待 Vercel 生产部署完成；
5. 直接访问公网项目页和文章页，确认请求全部正常返回。

### 最终成果

处理完成后，网站的个人项目区只展示我实际创建或参与维护的项目；Fork 不再混入个人作品，第三方 README 也不会再被当成我的项目介绍。

三篇整理后的文章已经同步到云端，旧博客与论文仅作为参考链接存在。项目说明、文章正文、GitHub 代码和 Turso 数据库之间也建立了可重复执行的同步流程。

这次经历让我意识到：个人博客的可信度不仅取决于页面是否漂亮、功能是否可用，还取决于内容归属是否清楚。对引用、Fork、协作项目和个人原创进行明确区分，本身就是项目规则和发布流程中不可缺少的一部分。
