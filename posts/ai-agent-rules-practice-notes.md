在个人项目里使用 Coding Agent 时，我反复遇到过几类问题：它不了解项目边界、重复引入已有能力、修改了无关文件，或者在缺少信息时直接猜测。

这些现象不一定说明模型能力不足。很多时候，真正缺少的是一份稳定、明确、可以随项目一起维护的上下文。规则文件的意义，就是把那些“Agent 不知道就很容易做错”的信息固定下来。

## 一、规则文件解决什么问题

新会话通常不会自动继承此前所有讨论。仅靠聊天里临时强调约束，时间一长很容易失效。

项目规则文件可以在每次工作前提供一份最小但稳定的说明，包括：

- 项目解决什么问题；
- 当前实际使用的技术栈与版本；
- 核心目录、数据入口和关键文件；
- 安装、开发、测试和构建命令；
- 代码风格、修改边界和验证要求；
- 遇到不确定情况时应当如何处理。

对我来说，规则文件不是“万能提示词”，而是项目自身的一部分。代码变化后，规则也需要跟着更新。

## 二、不同工具中的文件位置

| 工具 | 常见的项目规则文件 |
|---|---|
| Codex 及兼容工具 | `AGENTS.md` |
| Claude Code | `CLAUDE.md` |

如果同一个项目需要兼容多个 Agent，我更倾向于维护一份主要规则，再让其他入口引用它，避免两套规则长期漂移。具体引用方式应以工具当前版本的官方文档为准。

## 三、我会写进规则文件的内容

### 1. 项目目标

用一两段话解释业务场景、目标用户和明确边界。规则首先要让 Agent 知道“这个项目是什么”，而不是直接堆编码要求。

### 2. 技术栈与运行环境

准确写出语言、框架、运行时、包管理器、数据库和关键依赖版本。版本信息非常重要，因为新版本可能已经改变 API、目录结构或约定。

### 3. 架构与关键文件

列出真正重要的目录和数据流，让 Agent 能快速判断应该读取和修改哪里。例如：

```text
页面 / Route Handler
        ↓
业务与安全校验
        ↓
Prisma 数据访问
        ↓
SQLite / Turso
```

### 4. 常用命令

至少写明：

```bash
npm install
npm run dev
npm test
npm run lint
npm run build
```

如果项目还有迁移、索引、数据同步等特殊脚本，也应该说明其用途和风险。

### 5. 测试与验证

仅仅要求“改完代码”是不够的。规则需要告诉 Agent 如何证明改动有效，例如运行单元测试、生产构建、接口冒烟测试，以及检查移动端和桌面端页面。

### 6. 修改边界

我会明确要求优先复用已有组件、不要随意加入大型依赖、不修改生成目录，并保护用户已有的未提交改动。

### 7. 工作原则

比代码风格更重要的是决策方式：先理解再修改、优先最小改动、公开假设、遇到关键歧义时停止猜测，以及在完成后清楚说明验证结果。

## 四、规则不应该无限增长

规则越长，不一定越有效。大量低频信息会占用上下文，也会掩盖真正重要的约束。

我判断一条内容是否应该进入规则文件时，会问三个问题：

1. Agent 不知道它时，是否很容易犯错？
2. 它是否会在多个任务中重复出现？
3. 它是否仍然符合当前代码和部署环境？

如果三个问题都是否，这条内容更适合留在普通文档、Issue 或当前任务说明里。

## 五、从这次网站维护中得到的体会

这个个人网站在本地使用 SQLite 和 Ollama，公网则使用 Turso、OpenRouter 与 Vercel。聊天模型和 Embedding 模型必须分别配置；云数据库新增表后还需要实际执行迁移。

如果规则文件只写“这是 Next.js 项目”，Agent 就很容易忽略这些真实差异。有效的规则必须记录会改变决策的事实，例如：

- 写代码前读取当前 Next.js 版本自带文档；
- 本地数据库与公网数据库不是同一个运行环境；
- 密钥只能进入环境变量，不能提交 GitHub；
- Fork 和外部开源项目只能作为参考，不能放进个人原创项目列表；
- 文章迁移只保留作者自己的正文，旧博客主题和相关推荐不属于文章内容。

规则文件真正的价值，不是让 Agent 永远服从一套死规则，而是降低上下文缺失带来的误判。
